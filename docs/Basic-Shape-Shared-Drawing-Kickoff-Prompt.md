# Kickoff Prompt: The Shape Tools' Shared Drawing Behaviour

Last Updated: 09-12-26 10:12 · Revision 1.0

Paste everything below the line into a new Claude Code session rooted in this repository on the Linux machine. Start it only when no other session is committing in this working directory: this work changes all seven shape tools, `BaseTool`, the canvas view's foreground pass, and the status bar's hints, which every other session touches too.

This is the work the Eyedropper and Blur performance close-out named on 09-12-26 (`docs/Eyedropper-Blur-Performance-Implementation.md`, Section 11): the Basic Shape Annotation Tools PRD's Section 2, Shared Shape Behavior, whose drawing feedback and post-creation rules have been open since before the Basic Shape remainder work. Finishing it leaves that PRD with no open row in Section 2 and closes the last shared behaviour the seven shape tools do not have. `docs/General-UI-Implementation-Kickoff-Prompt.md` (revision 1.1) still governs the standards; this one governs the work. Where the two disagree, the general prompt wins and this one is corrected. The work is five phases and a close-out; a session pasting this prompt starts at the first phase not marked done in Section 1 of the notes document this work creates.

## Starting state, verified at commit 385c221 on 09-12-26

Verified by running the code, not by reading it. Three probes, each of which the first phase should turn into a test:

- **A drag on a locked or on a hidden layer creates the shape.** With the Rectangle tool and the active layer locked, a press, a move, and a release leave one item in the scene; the same with the layer hidden. 2.1 asks for the press to be refused with a status bar warning, and the Section 12 Shared Behavior row asks the same. The marker tools do make this check, through `check_requirements`; no shape tool does. The Blur PRD's 8.1 row claims the same rule for the Blur tool, which does not make it either.
- **A tool switch during a drag leaves the preview item in the scene.** With the Rectangle tool, a press and a move put the preview in the scene; activating another tool calls `cancel` and `deactivate`, neither of which the tool overrides, so the preview stays — in no layer's item list, behind no command, and undeletable by an undo. `is_active_operation` is False throughout, so the Space-bar pan and the momentary Alt eyedropper can also take the drag away mid-way.
- **Shift and Alt do nothing for the Rectangle and the Ellipse.** A move at 100 by 40 pixels with Shift held gives a 100 by 40 rectangle, where 2.3 asks for a square; a move with Alt held leaves the origin at the press point, where 2.3 asks for the centre. Both tools' idle hints already promise the modifier ("Shift: square", "Shift: circle"), so the hint is ahead of the code. The Line and the Arrow do constrain with Shift; the Arc constrains its chord with Shift and has no Alt; the Freehand has neither, and 9.5's straight segments are unbuilt.

The rest of the starting state, read from the code:

- No tool draws its preview at 70 percent opacity; the preview is the item with its final properties.
- There is no dimension tooltip anywhere, no constrain icon, no centre marker, and no guide line to the rulers. The Arc and the Polygon put their measurements in the status bar hint instead, which is a different place from the one 2.4 names; the Line, Arrow, Rectangle, Ellipse, and Freehand have static idle hints and no drawing hint at all.
- Every shape tool selects its new item and switches to the Select tool on release, against 2.1's last mouse-release step and 2.5's first two. `BaseTool._switch_to_select` reaches the window's tool manager, so this happens in the application and in `main_window`-based tests, and silently does not happen where the view has no main window. The Blur and Highlighter tools do the same; the Numbered Step, Stamp, and Emoji tools do not, as their own PRD's rapid-placement rule requires, and the Text and Callout tools select deliberately because their PRD puts a new item straight into edit mode.
- Snap to grid works during drawing: every tool maps the cursor through `_snap_pos`.
- **Alt does not reach the canvas on this machine's desktop.** `org.cinnamon.desktop.wm.preferences mouse-button-modifier` reads `<Alt>`, so Cinnamon starts a window move before an Alt+drag or Alt+click reaches the view. Doug's display run of 09-12-26 found it twice — the Zoom tool's Alt+click and the blur brush's Alt+paint eraser — and asked for a different key ("Alt still does not work. Lets use a different key, i am using linux, and it may not map"). Decision 4 settles what this work does about it for the centre-draw modifier.
- The suite at the last code commit (8a017bb) ran 1450 tests with 13 skipped and one environmental deselection: 1436 passed and one failed, the pre-existing timing-sensitive Zoom tool test, which passes alone. The run took 67 minutes. Ruff and mypy are clean. Commits f4260c4 and 385c221 add only documents.

## Decisions to surface

Apply the two-part test from the global guidance. Four decisions are expected to pass it; present all four with the consequential decision template before Phase 1 step 2 and wait.

- **1. Where the dimension tooltip is drawn.** 2.4 asks for a tooltip that follows the cursor at a 15 by 15 pixel offset and shows the shape's measurements as it is drawn. The example: dragging a rectangle over a screenshot to 320 by 240 pixels, watching the numbers, and letting go when they read right. Option A, a widget over the canvas view's viewport, as the Eyedropper's preview loupe is: the offset and the repositioning are arithmetic on the viewport rectangle, which is where 2.4's pixel measurements live; it is never a scene item, so no render can contain it; and the loupe's positioning, its Leave-event filter, and its painted shadow are all there to copy. Option B, the view's foreground pass, beside the grid, the guides, the crosshairs, and the layer hover outline: no new widget and no stacking order to think about, but every position is computed in scene coordinates and mapped back, which the zoom changes under you, and the text must be drawn unscaled by hand. Why it matters: this is the second overlay in two works, and if the two are built differently the next one has no pattern to follow; 2.4 also asks for the icon and the marker beside it, so whatever is chosen carries three things, not one. The cost of A: a second widget in the viewport's stacking order, which the panel-collapse modes and the focus frame must leave alone, and two overlay widgets that must not fight when the Eyedropper's loupe and a shape's tooltip could both be visible — they cannot today, since the Eyedropper draws nothing, but a later tool could. Recommendation: A, and factor the screen-edge positioning out of `loupe_overlay.py` so both overlays share one function rather than two copies of the same arithmetic. Follow-on detail: Technical Architecture PRD 3.9 gains the row either way, and Section 10 gains one module.
- **2. How far the not-auto-selected rule reaches.** 2.1 and 2.5 say the new shape is not selected and the tool stays active, so the user can draw another immediately; the code selects the shape and switches to the Select tool. The example: placing five arrows on a screenshot, which today takes five presses of A between them. Option A, every drawing tool: the seven shape tools, the Blur tool, and the Highlighter all stay active and leave their item unselected, which makes one rule for every tool that draws — the Numbered Step, Stamp, and Emoji tools already behave this way under their own PRD's rapid-placement rule, and the Text and Callout tools are excepted because their PRD puts a new item straight into inline edit mode. Option B, the seven shape tools only: the Basic Shape PRD's own scope, leaving the Blur and Highlighter as they are, since their PRD is silent on post-creation selection. Why it matters: rapid drawing is the reason 2.1 gives for the rule, and a rule that holds for five tools and not for two is the kind of thing a user cannot predict; it also changes what happens after every drag in the application, which is the most-used path there is. The cost of A: the Blur PRD gains a row where it was silent, and a user who draws one blur region and wants to resize it must now press V first — the same cost the shape tools pay. Recommendation: A, with the Blur PRD row. Follow-on detail: the tests that assumed the switch are rewritten rather than deleted, and the status hint after a draw should say the tool is still active, which the hint tables already imply by returning to the Idle row.
- **3. Whether 2.4's guide lines to the rulers are built.** 2.4's last bullet asks for dashed 1 pixel lines at 30 percent opacity in the accent colour, extending from the shape's edges to the rulers, when the rulers are visible. The example: drawing a rectangle that must line up with a button 400 pixels away, with the rulers on. Option A, build them in the view's foreground pass: the grid, the guides, and the crosshairs are already drawn there, the rulers' visibility flag is already read there, and the lines are scene-space lines from the shape's bounding box to the viewport edge, so they cost one more painter pass during a drag and nothing at rest. Option B, record them as a departure with a row: the ruler already draws a cursor marker that gives some of the same help, and the lines are the one bullet of 2.4 whose absence a user is unlikely to notice. Why it matters: it is the last unbuilt bullet of 2.4, so it decides whether this work closes the section or leaves a row open, and it is drawn during every drag, which is where the frame budget of Section 12's 60 frames a second row is spent. The cost of A: four more lines drawn per frame during a drag, and a decision about what "to the rulers" means when the rulers are hidden on one axis or the shape is off screen. Recommendation: A; the machinery is all in the place the lines belong, and leaving one bullet of five unbuilt would keep 2.4 open for the sake of a few lines of painting. Follow-on detail: the lines are drawn from the preview's bounding box, so they follow the modifiers for free, and they are a foreground pass, so no render of the scene can contain them.
- **4. Which key draws from the centre, given that Alt is taken by the desktop.** Every PRD in this project gives Alt the centre-draw meaning (Basic Shape 2.3, General UI 12.2), and on this machine Alt never reaches the canvas: Cinnamon's window manager takes Alt plus a mouse button as its window-move gesture, verified twice on this machine, and Doug's display run found it twice and asked for a different key. The example: drawing an ellipse from the centre of a button on a screenshot, which is the only way to place a circle on a known centre. Option A, keep Alt alone, as the PRDs say, and record that the gesture is unreachable on a desktop configured this way: nothing changes, the convention holds everywhere, and the user can clear one desktop setting to get it back. Option B, add Ctrl as a second route wherever a drawing tool reads Alt, Alt keeping its meaning: 2.3 reserves Ctrl "for future use, such as snapping to item edges" and no shape tool reads it today, so it is free; the centre-draw behaviour then works on every desktop without changing what Alt means anywhere. Option C, replace Alt with Ctrl in 2.3 and 12.2: one key per behaviour, at the price of changing a convention that is built and tested in the Select tool's point editing, in the blur brush's eraser, and in the Zoom tool. Why it matters: a modifier that cannot be pressed is a feature that does not exist for this user, and the same finding is open against the Zoom tool's Alt+click and the blur brush's Alt+paint eraser, so whichever way this goes sets the pattern for those two. The cost of B: two keys for one behaviour, which the hint text must name ("Shift: square | Alt or Ctrl: from center"), and Ctrl is then spoken for, so the edge snapping 2.3 reserves it for needs another key or a chord when it is built. Recommendation: B. It is the only option that gives Doug the behaviour today without breaking a convention that three other PRDs rely on. Follow-on detail: this work adds the second route in the drawing tools only; the Zoom tool's Alt+click and the blur brush's Alt+paint are named in the close-out as a follow-up, since they belong to other PRDs, and General UI PRD 12.2 gains one row describing the second route.

Everything else follows the PRDs; where they are silent or disagree, decide, note it under the notes' decisions section and the PRD rows, and continue. Silences known now:

- The locked and hidden layer check belongs in one place, not seven: a `BaseTool` helper the shape tools call from `mouse_press`, using `check_requirements` as the marker tools do, so the message reads as General UI PRD 1.3 asks and no control is disabled.
- The preview item is added to the scene during the drag, as it is today, rather than being drawn by an overlay: 2.1 calls it "a temporary preview item, not yet added to the scene's item collection", and the scene's item collection in this code is the layer's item list, which the preview never joins. The departure is in the wording, not the behaviour, and the 70 percent opacity of 2.4 is applied to that item and cleared when it is committed.
- A modifier pressed or released in the middle of a drag takes effect from that moment, without the drag restarting: the tools already recompute the geometry from the press point on every move.
- The Ellipse's Shift-held hint row of 6.7 reads a diameter, so a circle's tooltip and hint show `D:` where an ellipse's show `W:` and `H:`; the same rule gives the Rectangle's square no separate row, since 5.7 lists none.
- The Freehand tool's Shift segments snap to horizontal, vertical, and 45 degrees from the last direction change point, which 9.5 defines and 2.3's angle list does not: the Freehand keeps 9.5's four directions rather than 2.3's twelve.
- The tooltip shows the measurement only, and the status bar keeps the whole hint line with its modifier reminders: one function per tool computes the measurements, the tooltip shows them, and the hint text is built from the same values, so the two can never disagree.
- A shape too small to keep is still discarded on release, by each tool's own present threshold; 2.1's "bounding box area under 4 square pixels, or line length under 2 pixels" is recorded as a departure where a tool differs, as the Freehand's already is.
- The guide lines of 2.4 are drawn only while a drag lasts, never for a placed item, and only on the axes whose ruler is visible.
