## Decisions to surface

Apply the two-part test from the global guidance. Four decisions are expected to pass it; present all four with the consequential decision template before Phase 1 step 2 and wait.

- **1. Where the loupe is drawn.** The magnified window has to follow the cursor at sixty frames a second and must never reach a saved file. The example: dragging the Eyedropper across a 1920 by 1080 screenshot to find one pixel of a button's border. Option A, the view's foreground pass: `SnapView.drawForeground` already paints the grid, the guides, the crosshairs, and the layer hover outline, none of which reach an export, so the loupe joins a pass that is already correct about that; it repaints with the viewport and needs no new widget. Option B, a `QWidget` overlay over the viewport: it positions itself in widget coordinates, so keeping it on screen near an edge is arithmetic on the viewport rectangle rather than on the scene, and it can carry its own drop shadow through a graphics effect. Why it matters: 4.3 asks for a 120 px circle with a border and a shadow that stays on screen, and the choice decides whether the loupe is scene-space or widget-space arithmetic for the rest of the tool's life. The cost of A: the shadow and the border are drawn by hand, and every position is computed in scene coordinates and mapped back, which the zoom changes under you. The cost of B: a second widget in the viewport's stacking order, which the panel-collapse modes and the focus frame have to leave alone. Recommendation: B, since every measurement in 4.3 is in screen pixels and the repositioning rule is a screen-edge rule; Technical Architecture PRD 7.1 gains a row either way.
- **2. What the Eyedropper samples.** The colour under the cursor can be read from the scene or from what the viewport is showing. The example: sampling the border of a blue button on a screenshot while the grid is on and a selection handle sits nearby. Option A, the scene composite, as 4.2 says: render the sampled region through the render engine at canvas scale, so the colour is the canvas content and nothing else, and the loupe magnifies the same image. Option B, the viewport pixels: grab what is on screen, which is exactly what the user sees and costs nothing to produce, but includes the grid, the guides, the selection handles, the pasteboard beyond the canvas edge, and every tool overlay. Why it matters: this is what the tool is for, and it sets whether a sampled colour can ever be something the canvas does not contain. The cost of A: a render per mouse-move during a drag, which at an 11 by 11 sample plus the loupe's 15 by 15 window is a small region but still a render, and the loupe must be excluded from its own capture. Recommendation: A; 4.2 says "all visible layers composited together, including the canvas background", and a sampled grid line would be a bug the user could not explain. Follow-on detail: outside the canvas the sample is transparent, which 4.3 and 8.3 already describe.
- **3. How far the Eyedropper's Tool Options Bar goes.** The two PRDs describe different bars. The example: a user who wants the hex value of a colour on the clipboard without opening a dialog. Option A, the Blur PRD's 4.5 in full: the sampled swatch, the colour value field, the Color Format dropdown, the Sample Size toggles, the Apply Target dropdown, the Copy to Clipboard toggle, and the Color History row, with General UI PRD 5.3's shorter row corrected by a row, since each tool's own PRD owns its details (the Arc tool's Shift+A came the same way). Option B, the General UI row plus Sample Size and Color Format only, leaving the history, the clipboard toggle, and the apply target unbuilt and 4.4, 4.5, and 8.3 partly open. Why it matters: 4.5 is an eight-control bar on a tool whose bar has five widgets today, and the Tool Options Bar's overflow behaviour at a narrow window is already built and will be exercised. The cost of A: the widest bar in the application, and the Apply Target dropdown makes the two Apply buttons redundant, so they go and the General UI row is corrected twice. Recommendation: A. Follow-on detail: the Apply buttons are replaced by the Apply Target dropdown plus the apply-on-sample rule of 4.6, which is what 4.5 and 4.6 together describe.
- **4. How the Blur tool's 2.10 rows close.** The Gaussian meets the 100 ms target from radius 4 up and takes 154 ms below it, and 2.10 also asks for a background thread and a progress indicator past 2000 px. The example: dragging a 1000 by 1000 px blur region at radius 2 over a screenshot, where the region lags the cursor. Option A, the background thread of 2.10: render off the main thread with a progress indicator past 2000 px, the first thread in the code, showing a stale frame while it runs; it closes the row as written and covers every radius and every region size. Option B, no thread: measure where the 154 ms goes, cache the capture separately from the blurred result so a property change re-blurs without recapturing, and record 2.10's thread and progress indicator as a permanent departure with the measured figures. Why it matters: 2.10 is the last open row of Section 2, and a thread is a shape the codebase has deliberately avoided — the Check for Updates work chose Qt's signal-driven network module over a worker thread for that reason, and Technical Architecture PRD 9.1 would gain its first concurrency row. The cost of A: threading, its teardown on document close, and a stale frame the user sees; the cost of B: 2.10 keeps a departure row for ever, and a very large region stays slow. Recommendation: B, with the measurement first: the freeform blur work found that the capture, not the blur, is most of the time, so a capture cache may close the gap without a thread. If the measurement says otherwise, bring A back and say so.

Everything else follows the PRDs; where they are silent or disagree, decide, note it under the notes' decisions section and the PRD rows, and continue. Silences known now:

- The loupe over the pasteboard, beyond the canvas edge, shows the checkerboard and reports transparent, as 4.3 and 8.3 say for transparent canvas; the pasteboard's own colour is never sampled.
- `ApplyEyedropperColorCommand` (6.2) is built and replaces the `MacroCommand` of `ModifyPropertyCommand`s the Apply buttons push today, since 6.2 defines exactly that command with its own description; the undo entry's text changes and the behaviour does not.
- The Eyedropper joins the preset and theme model once 4.4's properties are creation defaults, so General UI PRD 5.2's line that "Select, Stamp, Blur, Eyedropper, Pan, and Zoom have no options to capture" is corrected by a row; `sample_size`, `color_format`, `apply_target`, and `copy_to_clipboard` are captured, and `last_sampled_color` and the colour history are not.
- The colour history is session state and is not written to `QSettings`, which 7.3 offers and does not require; it holds eight entries, newest first, de-duplicated by ARGB, as the picker's recent-colour list already does with twelve.
- Alt stands down during inline text editing (4.7). Whether it already does is checked in Phase 5 before anything is built for it; if a focused editor already swallows the key, the row is recorded as met and a test pins it.
- A sample size larger than 1 by 1 averages the red, green, and blue channels of every pixel in the area arithmetically, as 4.2 says, ignoring alpha in the average and reporting the area transparent only when every pixel in it is.
