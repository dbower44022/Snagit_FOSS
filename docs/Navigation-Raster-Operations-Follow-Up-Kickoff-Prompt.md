## Decisions to surface

Apply the two-part test from the global guidance. Three decisions are expected to pass it; present all three with the consequential decision template before step 2 and wait.

- **1. What a merge produces.** Option A, rasterize: Merge Down renders the upper layer's items, with its opacity and blend mode, onto a raster region on the lower layer, and the upper layer's items are gone; Merge Visible and Flatten All do the same across layers. This is Technical Architecture PRD Sections 3.2.2 and 3.7.3 as written ("vector items from upper layers are rasterized onto the lower layer's composite; destructive and undoable"), it bakes opacity and blend mode in exactly, and it is what Flatten All must do in any case; its cost is that a merged annotation stops being editable, which a screenshot annotator may not expect from "merge". Option B, move: Merge Down and Merge Visible move the upper layers' top-level items onto the lower layer, keeping them vector and editable, in stack order above the lower layer's items; only Flatten All rasterizes. This keeps every annotation editable and is one command over existing pieces (`MoveItemToLayerCommand` and `RemoveLayerCommand`); its cost is that the upper layer's opacity and blend mode cannot be kept on moved items (a Multiply layer at 50 percent merged down becomes plain items at 100 percent, unless the work bakes opacity into each item's own and drops the blend mode with a message), and that it departs from the two Technical Architecture sections, which need a change-log row. Recommendation: A; it is the PRD, it is exact, and Flatten All needs the rasterizing path anyway. Note the cost plainly in the Section 1.3 message: "Merge Down rasterizes the layer's items" is not a requirement message, so a one-time confirmation is a silence below.
- **2. What the layer type is.** Option A, a stored type: `layer_type` on the Layer per Technical Architecture PRD Section 3.2.1, written to `layers.json`, set by the code that creates the layer (Background by drop, paste, import, Flatten All, the library manager, the Snagit reader; Annotation by New Layer and Duplicate Layer; RasterRegion by nothing this work builds), with the BG badge read from it and the Background layer pinned to the bottom of the stack (Move Layer Down onto it refused with a message; Move Layer to Bottom lands above it). Option B, a derived kind: no stored field; a layer is a background when it is the bottom layer and holds exactly one raster region that fills the canvas, and the badge is computed. B stores nothing and needs no format change; its cost is that the kind flips when the user moves or resizes the region, that nothing pins the layer, and that the Technical Architecture model row stays unimplemented. Recommendation: A; the cost is one more field and the pinning rule.
- **3. Where the blend mode is applied.** Option A, per layer, exactly: each layer is composited as one image, on the display and in every export, as Technical Architecture PRD Section 3.9 says. On the display Qt's scene traversal cannot do this by itself; the work needs either a parent item per layer carrying a custom `QGraphicsEffect` that draws the layer's pixmap with the composition mode (which makes every layer's items child items, so every top-level walk of notes Section 17.2 changes meaning), or a view that draws each layer's items to an offscreen image itself. Exact, and the PRD; its cost is the largest change of this kickoff and the walk table's re-decision. Option B, per item, everywhere: the layer's blend mode becomes each item's painter composition mode in the item's paint pass, beside `layer_opacity` in `_apply_flip`, on the display and in every export alike. One line per item, consistent between display and export, no walk changes; its cost is that two overlapping items on the same Multiply layer multiply each other where the PRD says the layer composites once, and that Section 3.9 needs a change-log row saying so. Option C, exact in export and per item on the display: the smallest exact export; its cost is that the display and the export disagree on overlaps, which a user cannot see until they export. Recommendation: B; a blend mode on an annotation layer is rare, the overlap case rarer, and the one-line form keeps the display and the export the same. Record the departure in Technical Architecture PRD 1.15 and note that option A remains available when the layer-parent refactor is wanted for another reason.

Everything else follows the PRDs; where they are silent, decide, note it under the notes' Section 18 and the PRD 2.8 rows, and continue. Eight silences are known:

- Whether Merge Down asks before rasterizing: yes, once per session, a question with a "Don't ask again this session" checkbox; no when the setting Delete Layer confirmation is off. Recommended: ask, since option A loses editability and undo is the only way back.
- What Flatten All produces: one layer named "Background" of type Background holding one raster region the size of the canvas, the canvas colour painted first when it is opaque and left transparent when it is not, the layer active, and every other layer gone.
- What Merge Visible does with the active layer: the merged result layer becomes active; hidden layers keep their positions relative to it.
- Whether a merge bakes the group structure: yes under option A (a group is rendered like any item); under option B a group moves as one top-level item.
- What the canvas does when a background is created on an empty project: the canvas resizes to the image (Section 6.2, "fills the canvas exactly"), through the Resize Canvas command anchored top-left, in the same undo step. Recommended: yes.
- What drop and paste do when a Background layer already exists: a raster region on the active layer as today, never a replacement. Recommended: as today.
- Whether the RasterRegion layer type and its raster badge are assigned by anything: no; the type exists in the model and the badge in the delegate, and nothing this work builds creates such a layer. Record it so the Numbered Steps, Stamps, and Emoji or a later raster kickoff can decide.
- What the Zoom tool does when the desktop takes Alt+click: right-click zooms out as a second route, the status hint reads "Click to zoom in | Alt+click or right-click to zoom out | Drag to zoom region", and the momentary eyedropper is unchanged. Recommended: build it whatever the display check finds, since the desktop gesture is outside SnapMock's control.
