## Decisions to surface

Apply the two-part test from the global guidance. Four decisions are expected to pass it; present all four with the consequential decision template before Phase 1 step 2 and wait.

- **1. Where the shadow and the two opacities live.** The PRD gives all three items a shadow (enabled by default on numbered steps) and gives the numbered step and the stamp a fill opacity and a stroke opacity, and General UI Phase 6 decision 6.2 deferred the Property Panel's Shadow section and the two opacities to "the Basic Shape and Text PRDs' item work", which has not started. Option A, build them on the base classes now: `VectorItem` gains `fill_opacity` and `stroke_opacity` and `SnapGraphicsItem` gains the five shadow properties, painted for every item type, with the Property Panel's Shadow section and opacity sliders for every item; every item's paint pass and serializer changes, the walk table is untouched, and decision 6.2 closes for good. Its cost is the largest scope of any option, twelve item types re-tested, and a change to the file format of every type in the same commit. Option B, build them once as a shared helper the three new items use: `snapmock/items/shadow.py` (Section 10 row) with the shadow properties, their keys, and the painting, mixed into the three new items only, and `fill_opacity` and `stroke_opacity` on `NumberedStepItem` alone; the Property Panel shows the Shadow section and the two sliders when the selection's items all carry them. Its cost is that a rectangle still has no shadow after this work, so the Basic Shape work still owes the adoption, and the panel's sections depend on the item type. Option C, defer the shadow and the opacities for these three items too, with PRD rows: smallest; its cost is that the numbered step ships without the shadow the PRD turns on by default, and Section 8.1's "Shadow renders correctly for all badge shapes" fails on purpose. Recommendation: B; it builds what the PRD asks for exactly once, in a form the later item work adopts by mixing in, without re-opening twelve item types in a marker-tool kickoff. Under any option the shadow is painted in the item's `paint` (an offset, blurred copy of the shape from a cached `QImage`), not through `QGraphicsDropShadowEffect`, so the display, the raster exports, and the thumbnails agree; the SVG export draws no shadow, recorded as a deviation.
- **2. Where the emoji names, keywords, and categories come from.** The picker needs every emoji's category, name, keywords, and skin-tone capability. Option A, bundled Unicode data: `emoji-test.txt` from the Unicode emoji data (groups, subgroups, names, every sequence and its status) and the English CLDR annotations (keywords), converted once by a script under `scripts/` into one JSON under `snapmock/resources/emoji/` with a README naming the versions and the Unicode licence; about 1 MB of JSON, no runtime dependency, Technical Architecture PRD 9.1 holds. Its cost is a generator to maintain and a data version to bump when Unicode does. Option B, the `emoji` package from PyPI: names, aliases, and the modifier logic maintained upstream; its cost is a new runtime dependency that Section 9.1 allows only as optional, and the picker cannot be optional, so the package would be the first required package beyond the three; it also carries no CLDR keywords or categories, so Option A's category file is needed anyway. Option C, `unicodedata` names only: no data file, no dependency; its cost is that categories, keywords, and the emoji list itself are unavailable, so the picker would be a flat search over character names, which Section 4.2 does not describe. Recommendation: A; it meets Section 4.2 exactly with no dependency, and the data changes once a year.
- **3. Where the built-in stamps come from.** Section 3.3 asks for 50 to 60 SVG stamps across five categories. Option A, hand-authored: the session writes each SVG on the 64 by 64 viewport; its cost is fifty pieces of artwork whose quality the session cannot judge, and a week of the kickoff on drawing. Option B, Tabler Icons as the base: most of the named stamps exist as Tabler glyphs (circle-check, circle-x, alert-triangle, help-circle, info-circle, star, heart, thumb-up, thumb-down, the arrows, hand-finger, zoom-in, target, pointer, click, lock, lock-open, eye, eye-off, bolt, settings, pencil, trash, link, unlink, bookmark, message-circle, and more); the vendored subset under `resources/icons/tabler/` carries 106 of them (info-circle, eye, eye-off, lock, lock-open, pencil, trash, link, link-off, pointer, settings, plus, minus, x among them) and the rest are taken from the same Tabler release named in that directory's README, all copied into `resources/stamps/<category>/` under the MIT licence already in the tree with their stroke set to `#FF0000` so every one is colorizable; the stamps Tabler lacks (the DRAFT text stamp, the click and tap ripples, the starburst, the ribbon, the swooshes, the highlight rings) are hand-authored, about ten. Its cost is that the set reads as line icons rather than stickers, that "non-colorizable" is an empty class in the initial set, and that the Tabler README and the stamp README must both say which files are which. Option C, defer the artwork: ship the library with five placeholder stamps and a PRD row; its cost is that Section 8.2's first bullet fails and the tool is not useful until someone draws. Recommendation: B; the set is usable on day one under a licence already in the tree, and stickers can replace glyphs one file at a time later.
- **4. Whether the emoji font is bundled.** Section 4.7 says SnapMock bundles Noto Color Emoji as a Linux fallback. Option A, bundle it: `snapmock/resources/fonts/NotoColorEmoji.ttf` (10.8 MB) loaded through `QFontDatabase.addApplicationFont` when no colour emoji family is installed, with the licence files (the Debian copyright names Apache-2.0 and SIL OFL 1.1; the work reads the upstream licence and records which applies); its cost is 10.8 MB in the repository, in Dropbox, and in every wheel and installer, for a file every current Linux desktop, Windows 10, and macOS already have. Option B, do not bundle: `emoji_font_family()` returns the installed family (Noto Color Emoji, Segoe UI Emoji, Apple Color Emoji, or any family whose name contains "emoji") or None, and the tool explains "Emoji needs a colour emoji font installed" through the Section 1.3 message; a PRD 1.4 row records the departure from Section 4.7 and the acceptance bullet on the bundled font. Its cost is that a bare Linux container shows the message instead of emoji. Recommendation: B; the repository stays small and the missing case is a message, not a crash; Option A can be taken by a packaging kickoff that builds the AppImage, where the size belongs.

- The serialization `type` key: the class name, as every `ITEM_REGISTRY` entry; the PRD's `"numbered_step"` example gains a row. The Section 5 property keys are used as written.
- The Renumber command: Section 2.3 says a `MacroCommand` of `ModifyPropertyCommand`s and Section 6.1 defines `RenumberStepsCommand`; build `RenumberStepsCommand` in `snapmock/commands/marker_commands.py` (Section 10 row) beside `ChangeStampCommand` and `ChangeEmojiCommand`, each one command with its own undo, and a PRD row noting that 2.3's macro wording is superseded by 6.1.
- The placement animations (150 ms scale-up, 200 ms pop-in): a `QVariantAnimation` on the item's scale, started after the command is pushed, with a module flag the tests set so the item lands at scale 1 at once; not a command and not saved. The "Placed Step N" hint is shown for two seconds through the status bar's existing hint and then the tool's idle hint returns.
- The stamp's fill and stroke opacity of Section 3.5: not built; a stamp has one `opacity` per Technical Architecture PRD 4.3 and General UI PRD 8.3 ("Non-vector items (Stamp, Emoji, Blur) show a single Opacity slider"); the PRD row records that Section 3.5 and 3.6 disagree with both and that the single opacity wins.
- Custom stamp import routes: the Custom tab's Import SVG button and its drop target only; no File > Import row (File > Import Image imports images) and no Preferences > Stamps category (General UI PRD 11.3 lists none). A PRD row.
- Preferences > Emoji (the global skin tone): not built; the skin tone is remembered per session as Section 4.2 also says. A PRD row.
- The stamp cursor and the emoji cursor: the crosshair with a 24 px preview of the active stamp or emoji at the lower right, built in `ui/cursors.py`; the plain crosshair when none is selected.
- Double-click routing: today `SelectTool.mouse_double_click` owns double-clicks on items; a double-click on a numbered step, a stamp, or an emoji while the Select tool is active enters the item's edit (inline, the library, the picker) from there, and while the placing tool is active it does the same; one helper on the window, `open_marker_editor(item)`, serves both.
- The RasterRegion layer type (General UI notes Section 18.1, silence 7): nothing in this PRD creates a raster layer, so this work assigns nothing; the type stays for a later raster kickoff, recorded in the notes so the pointer stops here.
- Snagit export: `NumberedStepItem` and `StampItem` stay unsupported and `EmojiItem` joins them, with the writer's warning; no Snagit mapping is attempted.
- The 24 px minimum hit area: `shape()` returns the union of the item's shape and a centred 24 by 24 square when the item is smaller.
- The "Reset Size" context row: `stamp_size` back to the index's `default_size`, `emoji_size` back to 48, one `ModifyPropertyCommand`.
- Group members: a numbered step inside a group renumbers with the rest (the walk includes members); a stamp or emoji inside a group cannot be double-click edited without Ungroup, as the Group and Ungroup kickoff decided for every member.

## Standards that apply

- Terminology Precision, Writing Register, and Reply Format from the global guidance apply to every reply and to the documents.
- Every new module, resource directory, and data file gets a row in Technical Architecture PRD Section 10 in the commit that creates it; every new dependency is a decision (decision 2 is that decision, and its recommendation adds none).
- Departures from any PRD are recorded in that PRD's change log with a version bump, not only in code comments; a departure from the General UI PRD or the Technical Architecture PRD gets its row there as well.
- No control is disabled (General UI PRD 1.3); a control whose requirement is unmet says which, through `check_requirements`.
- Every new control, popover, and dialog gets an accessible name as it is created (`apply_default_names`), and `tests/test_accessibility.py`'s audit passes over every new surface.
- Every walk over the scene's items is added to the General UI notes' Section 17.2 table with which of the two walks it uses.
- `uv run ruff check .`, `uv run ruff format .`, `uv run mypy snapmock`, and `uv run pytest` must pass before each commit, with `QT_QPA_PLATFORM` set to `offscreen` for pytest.
- No test touches the network, the real application data directory, or the real font set without a skip guard.
- Commit messages end with the attribution block the session provides.
